# MongoDB support plan

Status: experimental native backend. SQL remains the default, and the Active Job adapter remains `:solid_queue`.

## Decision and scope

The native backend uses the MongoDB Ruby Driver for queue persistence and has no Mongoid integration. `config.solid_queue.backend = :mongodb` selects the native models, while `:active_record` preserves existing SQL installation and runtime behavior. SQL relation chains remain SQL-specific. Administrative consumers use `SolidQueue::Admin` for backend-neutral queries and actions.

| Component | Native behavior |
|---|---|
| Installation | `solid_queue:install --backend=mongodb` adds `mongo >= 2.24, < 3`, selects MongoDB in `config/application.rb`, and omits the SQL queue schema. Existing applications can install the driver and set the backend themselves. |
| Preparation | `bin/rails solid_queue:prepare` validates a transaction-capable replica set or sharded cluster and prepares collections/indexes. Queue access raises `SolidQueue::Mongo::ConfigurationError` when preparation is missing. Run prepare before producers or queue processes and on index-changing upgrades; the MongoDB update generator copies no SQL migrations. |
| Client | `MONGODB_URI` or `config.solid_queue.mongo_url` supplies the URI; `mongo_database` overrides its database. `mongo_client` supplies a client or callable. The backend needs no queue SQL configuration. Forked workers rebuild their client; size pools for the concurrent work of each process. |
| Job lifecycle | Atomic ready, scheduled, blocked, claimed, failed, and finished transitions use ownership/generation guards. Scheduled dispatch, bulk enqueue, queue ordering, pauses, concurrency semaphores, recurring deduplication, batches/callbacks, and process recovery use native operations. |
| Observability | Existing `*.solid_queue` lifecycle events continue; native IDs in model and notification APIs are strings. Claim events include candidate/claimed counts; transaction retry/deadline and driver health events expose contention and availability. Command monitoring is opt-in. |
| Backend contract | Workers, dispatchers, the scheduler, the supervisor, and the Active Job adapter call a fixed set of model operations. `test/shared/persistence_contract.rb` lists them and runs against both backends, and the `test/shared/*_behaviour.rb` suites run the same behavioural tests on SQL and MongoDB. A feature is only complete when both pass on both backends. |
| Administration | `SolidQueue::Admin` supports queue, job, batch, process, and recurring-task operations. The released dashboard consumer expects Active Record relations; its MongoDB-aware adaptation remains unreleased. |

## Persistence and lifecycle

A job document represents one execution attempt, with its state, claim, and failure fields. Batches, batch executions, semaphores, processes, pauses, and recurring records live in separate collections. Active Job retries can produce multiple attempts for one Active Job ID; batch logical totals deduplicate that ID across attempts. Failed jobs remain inspectable and manually retryable/discardable. A graceful shutdown releases claims; dead-process recovery fails lost claims under ownership guards, leaving retry policy to Active Job or an administrator.

Claims read indexed candidates, atomically mark ready documents with an owner, generation, and token, then read claimed documents by token. A stale owner cannot finish a newer claim. On an ambiguous claim outcome, token lookup resolves ownership instead of blindly repeating an `update_many`. Concurrency acquisition and the job transition share a transaction. Completion commits before releasing a semaphore and promoting blocked work; maintenance sweeps repair interrupted promotion and batch completion. Recurring `(task_key, run_at)` uniqueness and transactional enqueue prevent duplicate runs across schedulers. Batch membership and callback enqueueing use transactions and conditional completion.

Workers poll configured queues in order and sort jobs by priority, then ObjectId. ObjectIds are generated by clients, so equal-priority jobs created across processes within the same second do not have a global SQL-style insertion order. Public job, process, batch, and related queue-model identifiers are strings. Application consumers should use Admin operations rather than assume integer IDs or native Active Record relation methods.

Active Job payloads are stored as serialized JSON in each job document, preserving values such as integers larger than BSON int64 and the behavior of Active Job serializers. The MongoDB backend registers a serializer for nested `BSON::ObjectId` arguments. MongoDB limits a document to 16 MiB; enqueue checks the encoded document against that limit minus a 128 KiB lifecycle reserve and raises `SolidQueue::Job::EnqueueError` before writing. Constrained or batched enqueue rolls back together on rejection. Failure metadata is bounded to a 64 KiB envelope (1 KiB class, 16 KiB message, up to 64 backtrace lines of 512 bytes) so an admitted job can transition to failed.

Completed jobs follow `preserve_finished_jobs` and `clear_finished_jobs_after`. Keep the installed recurring finished-job cleanup task running; schedule `SolidQueue::Batch.clear_finished_in_batches` separately when retaining completed batches. Failed jobs and batches stay available for inspection. Run dispatchers with concurrency and batch maintenance enabled to recover stalled promotion/completion work. The indexes include state-specific claim/ready/scheduled/failed/retention paths and batch, process, semaphore, and recurring lookups; run `solid_queue:prepare` after an index-manifest update.

## Transaction and deployment rules

- Use a replica set or sharded cluster with transactions. A single-node replica set works in development; production failover and replication latency require their own deployment validation. `solid_queue:prepare` rejects a standalone server, and queue access checks topology and prepared indexes.
- Queue coordination uses primary reads and majority-acknowledged writes. Transaction retries and commit retries share a bounded deadline (`config.solid_queue.mongo_transaction_timeout`, default 5 seconds); a single attempt is not cut short by it. Transient transaction errors may rerun the body; unknown commit results retry commit rather than rerun the body. Keep external effects outside retried transactions.
- Use the same `Mongo::Client` and explicit `Mongo::Session` for atomic application data and queue writes. Scope enqueue with `SolidQueue.with_mongo_session(session, client: client)` inside the caller's transaction, and pass `session:` to raw driver writes. Sessions belong to their client and are not shared across concurrent threads or fibers.
- The Ruby Driver provides no commit callback for caller-owned transactions. Solid Queue leaves their deferred post-commit work to durable dispatcher batch/concurrency maintenance. For application data and queue storage on clients/databases that cannot share one transaction, use a transactional outbox when a loss-free handoff is required.
- Claims and majority durability protect queue state, not exactly-once external effects. Write idempotent jobs to handle retries. Before changing backends, stop new enqueues, drain or account for queued/in-progress/failed work, then switch producers and queue processes together. Retain the old store for inspection: changing backend settings does not transfer jobs.

## Verification status

Focused runtime checks passed for native lifecycle (4/24), large-integer retry (1/4), document/ObjectId/fork (5/18), concurrency (1/6), batches (1/7), recurrence (1/2), and Admin (5/15). The parenthesized values are tests/assertions for those focused checks, not coverage totals for their suites. A real Puma-plugin HTTP enqueue returned 202 and produced one MongoDB result through registered supervisor, dispatcher, and worker processes. The adapted dashboard was exercised in a real browser for parsed job arguments and retry, alongside other dashboard surfaces; the adaptation has not been released.

The repository provides native, race, runtime, and fault checks under `test/mongodb`, plus CI and `test/mongodb/run_matrix.rb` definitions for a pinned and a latest Ruby, Rails, driver, and server lane. Other combinations are untested. The comparative package under `benchmarks/` runs PostgreSQL and a single-node MongoDB replica set with equal resource limits and evaluates throughput and p99 claim latency. No comparative benchmark result or performance-parity claim is recorded here. The backend remains experimental while broader compatibility and comparative performance verification remain open.
